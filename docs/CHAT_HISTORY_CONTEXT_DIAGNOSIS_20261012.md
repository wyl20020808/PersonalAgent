# DEV 聊天卡顿与 OpenCode 历史诊断

用户反馈 DEV 界面卡死、内存超过 1 GiB，并主动强制关闭软件。本任务不恢复业务任务，不修改用户全局 OpenCode 配置，不产生新的付费模型调用。

## 证据

- 小地图原 Session 数据库有 628 条消息、592 个工具记录，没有 compaction 类型记录。最后成功的 assistant 请求报告普通输入 283、缓存输入 743168、输出 54；输入历史约 743K。缓存输入仍是参与请求的历史，不能把它等同于新增输入或账单金额。
- 私有只读服务探测确认自定义模型的 limit.context 与 limit.output 均为 0，表示元数据未知；不能据此宣称模型支持某个窗口。配置适配此前未传递用户的 compaction 设置。
- 两个业务审计文件约 61.3 MiB、56.7 MiB。聊天刷新、详情、图片证据多处同步全量解析与校验，阻塞 Electron 主事件循环；详情用量还会再次读取同一文件。用户关闭后，窗口已经不存在，故没有复测原来 1 GiB 的实际 Electron 占用，也不将崩溃日志直接解释为 OOM。
- 通过正式 stop 请求停止原 Run，检查 Controller、执行者、子进程和 Run 锁均已退出。两个原 Run、工作树、Session 和已有成果保留。没有重放中断工具。

## 修复范围

- 将聊天、详情、图片清单、原始证据和文件预览的 IPC 读取移到专用只读 worker。写操作留在原主服务，worker 拒绝写入请求，不启动监督或恢复任务。
- 相同在途请求合并，待处理请求限制为 32；关闭时拒绝等待请求并结束 worker。
- 审计分块解码，逐条验证完整 hash 链；最多保留两个文件、128 MiB 源数据的缓存。文件指纹变化重新验证，改写、截断、删除和伪造记录不复用旧缓存。普通追加读取采用确定的文件长度快照。
- 详情复用已验证审计统计用量，文件预览复用聊天投影，保留原始证据与文件归属检查。聊天投影缓存最多两个 Run。
- 保留原生压缩字段，并将 V2 keep.tokens、buffer 转为经本机 OpenAPI 验证支持的 preserve_recent_tokens、reserved。不猜测模型窗口，不重建会话。
