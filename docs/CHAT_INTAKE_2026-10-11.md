# 聊天统一指令入口

本轮在 `codex/chat-workbench-p0-p1` 任务工作区实现，未提交、合并或替换 MAIN/DEV 运行版。属于当前 Codex 会话开发和自主测试，没有启动真实付费 Agent 验收。

## 用户操作

输入区仅保留发送消息，不再选择“开发要求 / 补充需求 / 恢复”。新会话仍先选择项目，第一次发送才创建实际任务。旧的独立新建任务页面、导航和启动表单已移除；其他页面只导航回聊天，不直接创建任务。历史只读会话继续回放，不能借新入口扩大历史项目授权。

## 后台处理

- 空闲或上一轮完成：创建新 Run，将原文和附件交给现有决策者处理。
- 当前任务运行中：消息持久化排队；本实例 Controller 子进程正常完成后，按消息顺序继续处理。不会在工具调用中途修改正在执行的计划。
- 暂停、失败、停止后发送新消息：在同一个 Run 上恢复。“继续 / 重试”等简短指令恢复原检查点；有实质内容且节点允许返工时，进入原任务的执行流程，Agent 接收用户原文。
- 明确的短句“停止 / 暂停”：请求正式 Controller 停止，并保留待办但停止自动派发。包含这些词的普通需求不会被当成停止命令。
- 已有消息 ID 重复发送：校验文字和附件摘要，返回已有记录，不重复派发。
- 执行失败：保留消息及具体原因，支持在聊天中重试；不会把一次失败自动重放为无限循环。
- 应用重启、历史列表查询和轮询读取不会触发旧消息执行。异常暂停也不会用此前排队的文字自动授权恢复。

恢复时支持追加经过完整性校验的附件，保留原附件；同名同内容重试去重。每个 Run 的现有附件容量保护仍生效，超限明确报错。

## 边界

这是基于运行状态的调度层，用户请求的语义仍由现有 Agent 理解，并非新增一个能可靠识别所有自然语言的分类模型。运行中消息当前在任务正常完成后处理，不宣称支持原生工具执行中的实时插入。新任务和返工仍走原有 Controller 验收流程。

工作模式、不可恢复失败、执行/返工上限、项目互斥和隔离成果应用要求保持生效。普通聊天不会代替文档确认、已查看截图的视觉确认、人工验收摘要或交付批准。此类操作仍显示具体确认卡片或正式入口。
