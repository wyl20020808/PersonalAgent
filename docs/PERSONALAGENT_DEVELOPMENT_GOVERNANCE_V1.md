# PersonalAgent — MAIN/DEV/TEST 三分支开发与使用治理规则 V2

版本：V2。修订日期：2026-10-11。适用范围：PersonalAgent 自身开发、维护、试用、救援、集成和正式发布。沿用 V1 文件路径，保证既有引用有效。

本次按用户决定全面替换原双版本职责与流程：MAIN 暂留稳定版本；DEV 执行真实任务；TEST 持续集成与试用；当前外部 Codex 开发会话负责迭代，不要求 MAIN 发起。新功能以 TEST 为基线，先交付 TEST，完整候选验收后在安全节点交付 DEV。本文建立治理约定，不声明 TEST 分支、启动入口或三实例运行隔离已经实现。

## 2026-10-11 流程上限与执行模型修订

用户明确决定：桌面端 Run 不再设置执行轮数、返工次数和审查修复次数上限，由用户在聊天中自行停止或调整；桌面端规则优先于历史版本中的流程上限表述。Controller 配置中的 `maxLoops`、`maxReworks` 改为可选，仅在脚本或 CLI 显式配置时生效；恢复旧 Run 时桌面端移除其已保存的上限并写入审计。用量计数、超时、并发写入锁、数据隔离及正式成果审批不变。

同时允许用户在 Run 暂停、失败或停止时切换执行后端或模型后继续：切换写入审计，已有文件修改保留，新模型使用新的执行 Session；决策者身份锁不变。影响：自动“审查—返工”循环不再自动暂停，真实调用的次数完全由用户把控。

## 2026-10-11 单决策者切换修订

用户明确授权实现单决策者任务的中途切换：只允许在暂停、失败或停止且旧调用和进程已退出后，通过正式切换入口操作。切换须保存交接记录与旧身份、Session 审计；保留同一 Run、工作区、执行者 Session、已完成项、计数、验证证据与交付审批边界，新决策者使用新的 Session 接手未完成节点。除该显式切换入口外，决策者身份校验继续生效。多决策者任务仍禁止中途切换。本条取代上一修订中单决策者“决策者身份锁不变”的限制；不授权合并、推送、发布或修改运行中的 DEV。

## 2026-10-11 真实验收与连接恢复修订

用户持续授权在已授权任务范围内使用已配置的真实模型及真实场景进行开发、调试、测试和验收，允许消耗 Token，要求尽量减少无必要消耗。具体执行遵循统一 Agent 工作规则第 11 条。历史章节中的“本次不调用真实付费 Agent”仅描述对应历史任务，不作为后续任务的通用禁令。本授权不扩大提交、合并、交付、推送、发布或系统操作权限。

短暂连接异常应先由服务端或 CLI 原有机制恢复；重连进度不等于失败。调用真正结束后，可以在同一 Run、角色和 Session 内有限恢复，不计作业务返工；恢复记录、调用用量和已有修改必须保留。未知工具结果、进程状态不明、Session 归属异常仍需明确恢复指令，禁止盲目重放。该条允许实现自动恢复，不声明未验证的后端已经具备能力；实现范围与验收结果见任务验证文档。

## 一、规则入口与授权边界

所有参与 PersonalAgent 开发的 Agent，首次参与任务，以及执行分支操作、修改源码、创建 Worktree、集成或发布前，必须读取本文件全文、AGENTS.md 和 AGENT_WORK_RULES.md；Claude Code 同时遵循 CLAUDE.md。续接任务确认规则版本，不以摘要、链接或历史报告代替当前规则。

既有分支和 Worktree 不自动获得新规则。开展新任务前核对规则版本，在授权范围内接入当前规则，或显式提供全文并记录版本；不得继续使用旧的日常开发基线约定。不因本文修订批量覆盖其他任务目录或用户修改。

Agent 不自行提交、合并或应用成果到源项目。本文所称提交、整合、交付和发布均须遵守 Controller 正式交付审批，由获授权执行方实施。开发验收通过不等于交付获批；MAIN 正式发布还须用户明确批准。外部 Codex 开发会话不能冒充 PersonalAgent 真实 CC/Codex Run 或 Controller 独立验收。规则修改授权不等于 TEST 建设、迁移数据、启动实例、源码交付或发布授权。

同一 Run 内 Controller 顺序调度 Agent，一次调用结束后才派发下一次，不留下后台写入进程；跨任务并行各用独立分支和 Worktree。独立验收期间不修改被验收工作区。

默认使用脚本、CLI、API 或正式 Controller 接口操作 PersonalAgent，已授权目录和执行方式不重复要求 GUI 确认。遵守全局工作/空闲策略及 Hook，Agent 不修改或绕过策略。work 下可见 GUI 验收记录 deferred_by_work_mode 并延后，继续不依赖 GUI 的开发和普通检查；pending 不称为 PASS。系统高风险操作须另行明确授权。

2026-10-09 已移除内部付费预算保护与预授权门槛。MAIN、DEV、未来 TEST 和 CLI 可使用已配置的真实 Agent，不要求预算授权文件、预设调用次数或余额。历史预算、Run、Session、凭据及审计保留；用户对任务单独明确设置的调用限制仍须遵守，不通过多实例、多 Run 绕过。用量计数、超时、写入锁、隔离和审批不变；桌面端不设执行轮数、返工次数及审查修复次数上限，脚本或 CLI 显式配置的上限才生效。认证、限流及订阅额度错误正常报告。未来预算功能独立设计为可选功能。本规则不扩大推送或发布权限。

## 二、分支职责与任务基线

### main：稳定版本保留

- 保留经用户认可的稳定版本及必要启动、恢复配置，当前暂不参与日常迭代，不要求运行 MAIN 实例。
- 未来可用于稳定使用、救援和调度自身维护；发起软件版本不改变开发基线。
- 不直接在 main 工作区开发日常功能。只有达到正式稳定标准且用户明确批准，才将已验收的 dev 版本发布 main。

### dev：真实任务执行版本

- 用于开发 OpenWorld、FPSArena 等实际项目，任务期间固定正在运行的软件版本。
- 接收 TEST 已验收的明确候选版本，或经独立验收的 DEV 紧急修复；不承担持续集成和未验收新功能试用。
- 安全更新前保存检查点、停止相关写入和检查数据兼容性，更新后核查历史 Run/Session 恢复。

### test：持续集成与新功能试用版本

- 日常新功能和普通修复以最新 test 的明确提交为基线。
- 接收经过任务检查、审查及正式交付审批的 feature/fix 成果；整合后验证组合效果，供用户及时试用。
- 持续积累新功能，运行数据隔离，不打断 DEV 真实任务。默认按完整验收批次交付 DEV，未验收功能不得夹带。

### feature/*：新功能任务

从最新 test 的明确提交创建独立分支和 Worktree。由获授权外部 Codex 开发会话或 PersonalAgent 正式流程开发、测试和审查；通过必要验收与正式交付审批后先整合 test，不直接交付 dev 或 main。

### fix/*：普通修复及 DEV 紧急修复

- TEST 普通问题从最新 test 创建独立 fix，验证和审批后先回 test。
- DEV 真实任务受阻的紧急软件问题从当前 dev 明确提交创建独立 fix，避免引入 TEST 未验收功能。实际运行构建落后于 dev 时，先记录运行提交并复现核对差异。
- DEV 紧急修复独立验收和交付获批后，在安全节点更新 dev，再同步必要修复回 test，并检查冲突和组合效果，防止后续 TEST 更新覆盖修复。

### hotfix/*：MAIN 紧急修复

仅 main 稳定版本确有紧急问题时从其明确提交创建。验证、修复确认及用户明确发布批准后更新 main；必要修复按实际差异同步 dev、test，各自验收和审批，不豁免发布要求。

任务记录分别写明开发执行方/发起软件版本、Git 基线分支与提交、实际运行构建提交。外部 Codex 或 MAIN 软件发起任务不决定 Git 基线。新任务分支使用 feature/*、fix/*、hotfix/*，既有历史分支不擅自改名或删除。

## 三、工作目录与运行隔离

长期目标路径如下；约定不代表分支或目录已存在：

- MAIN 源码：`D:\PersonalAgent`，长期保持 main。
- DEV Worktree：`D:\PersonalAgent-worktrees\dev`。
- TEST Worktree：`D:\PersonalAgent-worktrees\test`。
- 独立任务 Worktree：`D:\PersonalAgent-worktrees\tasks\<TASK_ID>`。

创建前核对实际路径、分支、提交、已有 Worktree、用户修改及任务归属。同名路径或分支存在时不得覆盖或重置。日常源码开发使用独立任务 Worktree，禁止频繁切换正式目录分支开展并行开发；规则文档按用户明确授权修改，不据此扩大源码开发范围。

不覆盖正在运行的软件源码、构建产物或状态文件。各环境独立管理可写构建产物、配置、Electron 状态及单实例锁、Session、Run、Controller runtimeDir、日志、缓存和临时目录。runtimeDir 位于目标项目外的 D 盘。TEST 不复用 DEV 可写目录，不为试用迁移、清空或改写真实任务历史。

当前 MAIN/DEV 接口见 DUAL_INSTANCE_RUNTIME_V1.md。TEST 启动入口、实例身份、运行隔离及三实例并存须实际实现和验收；创建 test 分支不等于完成隔离，配置入口不等于能力已验证。不假定已有 HTTP 端口；若新增监听服务，另行检查端口冲突。

并发实例不无协调地写同一目标项目；开始任务前指定写入方、锁和安全交接时点，不能将实例内部锁当作已验证跨实例互斥。认证可使用已授权本机配置，不擅自复制或提交凭据；认证共享与业务状态隔离分别核验，竞争时保留现场并安全协调。

Worktree 是 Git 协作隔离，不是操作系统权限沙箱。Controller isolated 克隆或副本不自动等同本规则布局，须通过正式实现验证映射，不绕过恢复或验收机制。任务结束保留 Diff、基线、验收和审计证据，再按批准清理流程处理；不擅自删除其他 Worktree、用户文件或未提交修改。

## 四、日常开发与 TEST 集成

1. 用户明确改进目标、范围和验收标准；当前可由外部 Codex 承接，不要求 MAIN 启动。
2. 核对最新 test、用户修改及任务归属，从明确 test 提交创建 feature/fix 分支和独立 Worktree。TEST 尚未建立时报告，不自动退回旧的 DEV 日常开发流程；由另行授权建设任务确定初始基线和目录。
3. 使用原生工具开发、调试、测试，保留真实操作与结果。通过 PersonalAgent 执行时走正式 CC/Codex/Controller 流程；外部开发会话如实标明执行方式。
4. 执行适用的独立验收和审查；审查修改后复验最终内容，不把开发者自测称为 Controller 独立验收。
5. 按正式交付审批形成可追溯成果，核对最新 test 与整合差异，获批后在安全节点整合 test；基线变化时补做必要验证。
6. 检查合并后的 TEST 组合效果，并实际试用功能、GUI 和运行情况。GUI pending、失败及覆盖不足如实记录，单个任务检查不能代替集成验证。
7. TEST 可继续迭代，DEV 保持运行版本；TEST 一次试用成功不自动触发 DEV 更新或 MAIN 发布。

## 五、TEST 交付 DEV

1. 选定 TEST 明确候选提交和完整批次，记录相对 DEV 的全部变更、来源任务、依赖及验收证据。
2. 批次内全部功能通过适用测试、审查及实际验收后才交付；TEST 含未验收功能时，不直接整体合并 DEV。
3. 默认整批验收、整批更新。确需部分交付时，另建候选分支核对依赖，独立验证最终组合并取得对应审批；cherry-pick 成功不代替验收。
4. 核对 DEV 自候选基线以来的紧急修复，在 TEST 或候选版本保留这些修复并复验，防止旧缺陷重新进入 DEV。
5. DEV 所有关联任务须完成或到可安全暂停、恢复的节点；保存 Run/Session、检查点、日志及必要备份，仍有写入进程时不得替换源码或构建产物。
6. 正式交付获批后由获授权执行方整合 DEV、构建并安全重启，记录来源提交、Diff 和回滚版本。基线或范围变化时重新核对审批及验收。
7. 核查真实任务恢复、数据格式、日志、历史用量和状态兼容性。不能可靠恢复时保留现场并报告，不重放已完成操作，不自动删除历史数据。

TEST 可继续开发，但交付验收绑定的候选提交保持不变，被验收工作区冻结。Git 整合与运行版本升级分别记录，不通过改动活跃 DEV 工作区实现即时试用。

## 六、故障处理及修复同步

先保存异常 Run、Session、工具事件、文件状态、运行提交和已执行操作，区分 PersonalAgent、Agent 服务与目标项目故障。DEV 软件故障按 DEV 紧急 fix 流程处理，TEST 故障按 TEST 普通 fix 流程处理；当前由外部 Codex 承接，不依赖 MAIN 自动接管。

必要故障信息通过已授权方式脱敏交接，不传播凭据或敏感日志。自动故障发现、上报、诊断转交、恢复编排及跨实例接管只有实际实现并验收后才能称为产品能力。中断保留原 Run/Session 和部分写入，不自动重建任务、重置计数或回放已执行操作。

## 七、DEV 发布 MAIN

当前 MAIN 暂时保留，不因 TEST 或 DEV 更新自动发布。未来正式发布至少满足：

- 完整 Controller 回归、GUI 单元与集成测试、实际 Electron 关键交互检查通过。
- 原有主要功能无明显退化，必要 UI 修改经过真实界面检查。
- 任务恢复、日志、历史用量及数据兼容性经过检查。
- 变更文件、Diff、验收版本和来源提交可追溯，保留可恢复稳定构建与必要状态备份。
- 用户明确批准绑定具体 DEV 待发布提交和范围的正式发布；范围变化重新确认。

发布前检查 main/dev/test 状态和用户修改，按正常 Git 历史整合，不强制覆盖 main，不丢弃用户修改，不默认 push。正式发布授权不含自动远程推送或部署。发布期间保持安全更新状态，失败优先恢复已验证版本；数据格式变化须检查备份与兼容性，不只回退代码后声称数据已恢复。无法可靠回滚时保留现场并报告。

## 八、协作、证据与规则维护

Claude Code 主要规划和审查，也可必要修改；Codex 主要实现、调试和测试；Controller 负责正式调度、独立验收、恢复、审计及交付审批；用户决定目标、重大变更及正式发布。分工不限制原生工具能力，也不授权修改无关项目。当前外部 Codex 执行方式不削弱正式交付边界，游戏等真实项目仍按 AGENTS.md 使用 PersonalAgent 正式流程。

重叠文件明确集成顺序、责任方和检查范围。整合前核对目标分支当前提交、基线变化、用户修改与最终结果，整合后验证组合；不能可靠解决冲突时保留现场并报告，不舍弃任一方修改。

记录任务 ID、执行方、基线、任务分支、Worktree、实际运行版本、变更、检查、审查、审批和发布决定。只读或文档修改没有 Run 时如实说明，不制造虚假 Run；不把 Mock、历史日志、自测或 Delivery Preview 冒充真实 Agent、独立验收或正式交付。不提交凭据、认证副本或敏感日志，添加文件前逐项核对，不批量纳入整个工作区。

规则修改须记录版本、日期、原因与影响，并检查 AGENTS.md、CLAUDE.md、统一规则、两份执行契约、README.md 和运行说明的一致性。历史验收报告与审计保留原事实，仅作为对应版本证据，其旧分支流程不得指导新任务。原 V1 接入快照及待建 DEV 清单不再作为当前规范，历史内容可从 Git 历史查询。重大权限、发布或用户数据政策变化仍须用户批准。
