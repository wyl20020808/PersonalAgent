# PersonalAgent — Main/Dev 双版本开发与自我迭代治理规则 V1

版本：V1（2026-10-09 付费预算策略修订）。制定日期：2026-10-09。适用范围：PersonalAgent 自身开发、维护、试用、救援、集成和正式发布。

本规则建立长期治理约定，不声明相关分支、目录、并发管理或自动故障上报已经实现。main 负责稳定运行和维护，dev 负责实际试用，feature/fix 负责开发，用户批准后才从 dev 发布到 main。

## 2026-10-09 付费预算策略修订

用户明确决定暂时完全移除 PersonalAgent 内部付费预算保护与预授权要求。本文旧条款中要求“已有预算授权”、共享付费账本或按内部额度预约派发的内容由本条取代：MAIN/DEV 使用已配置的真实 Agent，不需要预算授权文件、预设调用次数或余额。历史预算、Run、Session、凭据和审计保留。执行轮数、返工次数、超时、并发写入锁、数据隔离及正式成果审批不变；服务商错误正常报告。用户对某项任务另外明确设置的调用限制仍须遵守，未来预算功能须独立设计为可选功能。本修订不扩大提交、发布或远程推送权限。

## 2026-10-11 流程上限与执行模型修订

用户明确决定：桌面端 Run 不再设置执行轮数、返工次数和审查修复次数上限，由用户在聊天中自行停止或调整；本条取代上一修订中“执行轮数、返工次数……不变”的表述。Controller 配置中的 `maxLoops`、`maxReworks` 改为可选，仅在脚本或 CLI 显式配置时生效；恢复旧 Run 时桌面端移除其已保存的上限并写入审计。用量计数、超时、并发写入锁、数据隔离及正式成果审批不变。

同时允许用户在 Run 暂停、失败或停止时切换执行后端或模型后继续：切换写入审计，已有文件修改保留，新模型使用新的执行 Session；决策者身份锁不变。影响：自动“审查—返工”循环不再自动暂停，真实调用的次数完全由用户把控。

## 2026-10-11 真实验收与连接恢复修订

用户持续授权在已授权任务范围内使用已配置的真实模型及真实场景进行开发、调试、测试和验收，允许消耗 Token，要求尽量减少无必要消耗。具体执行遵循统一 Agent 工作规则第 11 条。历史章节中的“本次不调用真实付费 Agent”仅描述对应历史任务，不作为后续任务的通用禁令。本授权不扩大提交、合并、交付、推送、发布或系统操作权限。

短暂连接异常应先由服务端或 CLI 原有机制恢复；重连进度不等于失败。调用真正结束后，可以在同一 Run、角色和 Session 内有限恢复，不计作业务返工；恢复记录、调用用量和已有修改必须保留。未知工具结果、进程状态不明、Session 归属异常仍需明确恢复指令，禁止盲目重放。该条允许实现自动恢复，不声明未验证的后端已经具备能力；实现范围与验收结果见任务验证文档。

## 一、规则入口与既有约束

所有参与 PersonalAgent 开发的 Agent，首次参与任务，以及执行分支操作、修改源码、创建 Worktree、集成或发布前，必须主动读取本文件全文、根目录 [AGENTS.md](../AGENTS.md) 和 [统一 Agent 工作规则](../AGENT_WORK_RULES.md)。续接任务时应确认规则版本是否变化；不能将摘要、Markdown 链接或上下文中的部分内容当作全文读取。

Claude Code 同时遵循根目录 [CLAUDE.md](../CLAUDE.md) 的导入要求。任务工作区必须包含与任务基线对应的规则；旧分支缺少规则时，应先在授权范围内接入或显式提供规则并核对版本，再开展开发。不得假设主目录的新文件已自动出现在既有 Worktree 中。

本规则与统一工作规则及现有 [项目执行契约](../PROJECT_EXECUTION_CONTRACT.md) 配合执行：

- Agent 不自行提交、合并或应用成果到源项目。下文“形成提交”“整合”“发布”均指经 Controller 正式交付审批后，由获授权的执行方实施，不是向 Agent 授予自动交付权。
- 开发验收通过不等于正式交付获批，整合到 dev 也须遵循已有交付审批；发布 main 还必须取得针对正式发布的用户明确批准。
- Controller 在同一 Run 的工作区顺序调度 Claude Code 和 Codex；一次调用结束后才能派发下一次调用，不得留下后台写入进程。不同任务可在独立分支和 Worktree 中并行，独立验收期间不得修改被验收工作区。
- 已授权的目录、预算和执行方式可通过脚本、CLI、API 或正式 Controller 接口直接使用；不重复要求 GUI 确认。预算扩大、重大变更、远程推送、发布和正式成果审批仍按原规则执行。
- 遇到冲突时记录相关文件、具体条款和影响，先在既有授权范围内处理。无法可靠处理时停止受影响的操作并报告；不得自行忽略原规则或降低要求。

## 二、分支职责

### main：稳定正式版本

- 始终代表经过用户认可的稳定版本，主要用于正常使用、维护、修复和调度 PersonalAgent 自身开发。
- 不直接在 main 工作区进行日常功能开发；通过独立任务分支及 Worktree 开发。
- 只接受已通过验证且获得用户明确发布批准的更新。
- dev 故障时应能作为稳定救援入口；保留可启动、可恢复的已验证版本及其必要运行配置。

### dev：长期开发与试用版本

- 用于日常试用，也可通过 dev 软件开发 FPSArena、OpenWorld 等其他正常项目。
- 接收经过测试、审查及正式交付审批的 feature/fix 成果。
- 可持续积累新功能和修复，不要求每次更新都发布 main。
- 未经用户明确确认，不得自动发布到 main。

### feature/*：新功能任务

- 从当前最新 dev 的明确提交创建，用于 PersonalAgent 新功能开发。
- Claude Code 和 Codex 在该任务的独立 Worktree 中开发、测试和审查；同一任务内遵守 Controller 顺序调度。
- 完成验收和交付审批后，在安全时机整合到 dev。

### fix/*：dev 问题修复

- 从当前最新 dev 的明确提交创建，用于修复 dev 使用过程中发现的问题。
- 即使由 main 软件发起和调度，代码基线仍来自 dev；不得改用 main 基线而遗漏 dev 的问题上下文。
- 验证和审批通过后整合回 dev。

### hotfix/*：稳定版紧急修复

- 从 main 的明确稳定提交创建，用于 main 自身的紧急问题。
- 通过验证、修复确认和用户明确发布批准后更新 main；紧急情况不自动豁免正式发布要求。
- 同步必要修复到 dev，检查冲突和兼容性，避免版本分叉；同步也须验收及审批。

任务记录必须分别写明“发起任务的软件版本”与“Git 开发基线分支和提交”。main 软件可以调度基于 dev 的 feature/fix；软件版本不决定分支来源。新任务分支按 feature/*、fix/*、hotfix/* 命名，既有历史分支不因此擅自改名或删除。

## 三、工作目录管理

长期目标路径如下，路径约定不代表目录目前存在：

- 正式源码：`D:\PersonalAgent`，长期保持 main。
- dev Worktree：`D:\PersonalAgent-worktrees\dev`。
- 独立任务 Worktree：`D:\PersonalAgent-worktrees\tasks\<TASK_ID>`。

每个并行开发任务使用独立分支和 Git Worktree。禁止多个任务无协调地修改同一源码工作区，禁止通过频繁切换正式目录分支开展并行开发。创建前核对真实目录、分支、提交、已有 Worktree、用户修改及任务归属；存在同名路径或分支时，不得覆盖或重置。

不允许直接覆盖正在运行的软件源码、构建产物或状态文件。任务完成后保留必要提交、Git Diff、基线、验收结果和审计证据，再按批准的清理流程处理任务目录。不得擅自删除其他 Worktree、用户文件或未提交修改。

独立任务 Worktree 是 Git 协作隔离，不是操作系统级权限沙箱。Controller 现有 isolated 模式可能使用克隆或文件副本，不能直接宣称它已实现本规则的任务 Worktree 布局。未来建立流程时应使用正式实现并验证工作区映射，不能绕过调用计数、恢复或验收机制。

## 四、main 与 dev 同时运行

治理上允许 main 与 dev 同时启动，实际启动前必须验证运行目录、状态隔离和现有单实例机制。典型场景是 main 调度 CC + Codex 开发 PersonalAgent，dev 同时调度 CC + Codex 开发其他游戏或软件；feature/fix 修改发生在独立 Worktree，不直接修改运行中的 dev。

并发运行必须满足：

1. 两版本各用独立可写的 Session、Run、日志、缓存、临时文件和 GUI 状态目录；源码、构建产物、配置与运行目录均有明确归属。Controller 的 runtimeDir 保持在目标项目外，并符合现有 D 盘约束。
2. 不允许两个版本同时无协调地修改同一个目标项目；不能把实例内部的锁当作已验证的跨实例互斥。开始任务前核对另一实例任务，指定写入方和安全交接时点。
3. 共享真实模型账户或总体调用预算时，必须共同遵守用户授权额度；不得通过两个实例、多个 Run 或重新创建预算账本绕过同一额度。现有账本覆盖范围不足时，在统一核算方案确认前不得启动超出可确认额度的调用。
4. 认证可使用用户已授权的本机配置，不得擅自复制或提交凭据。认证目录共享与业务运行状态隔离是不同问题；发现认证状态竞争时应保留现场并安全协调。
5. 更新 dev 前核对所有相关任务是否处于可安全停止、暂停或恢复的状态，保存检查点和操作证据；仍有写入进程时不得替换代码或构建产物。
6. dev 更新后重新启动，核对历史 Session、Run、预算、日志及状态兼容性，并检查原有任务恢复情况。

同时运行是本规则允许的目标，不等于已完成双实例运行验证。不得仅因存在配置入口就宣称状态隔离、跨实例预算或互斥已验收。

## 五、PersonalAgent 自我迭代流程

正常新功能流程：

1. 用户在 main 软件提出 PersonalAgent 改进需求，明确目标和已有预算授权。
2. main 调度 Claude Code 规划任务，记录发起软件版本、需求、任务边界和验收标准。
3. 核对最新 dev、用户修改及任务归属，从明确的 dev 提交创建 feature 分支和独立 Worktree。
4. Codex 和必要时的 CC 使用原生工具开发、调试、测试，保留真实工具事件及结果。
5. Controller 执行独立验收，CC 审查；审查产生修改后，Controller 重新独立验证最终内容。
6. 验收通过后，按正式交付审批形成可追溯提交；Agent 不因完成自测而自行提交。
7. 检查最新 dev 和整合差异，在 dev 可安全更新且交付获批时整合；基线变化时补做必要验证。
8. 使用 dev 软件实际检查功能、GUI 和运行情况，核对任务恢复、预算与数据兼容性。
9. 用户决定继续迭代或保留当前 dev 成果；dev 可以积累多次成果。
10. 只有达到正式稳定标准并取得用户明确发布批准，才按发布流程更新 main。

Agent 判断“开发完成”、Git 提交成功、CC 审查通过或 dev 一次试用成功，都不能自动触发 main 升级。

## 六、dev 故障救援流程

dev 开发其他项目时出现问题，按以下流程处理：

1. 优先保存 Run、Session、工具事件、异常日志、文件状态、当前提交和已发生的操作；避免继续写入扩大影响。
2. 区分 PersonalAgent 软件故障、Agent 服务故障与目标项目代码故障，明确故障归属，不能将所有失败都当作 PersonalAgent Bug。
3. 将必要的脱敏故障信息交给 main 版本，记录版本、任务、复现条件、检查点和已完成操作；不得擅自传播凭据或敏感日志。
4. 确认为 dev 的 PersonalAgent 问题后，由 main 从当前 dev 创建 fix 分支和独立 Worktree。
5. CC 分析原因，Codex 修复并测试；必要时 CC 直接修复。相关调用继续遵守授权预算和正式流程。
6. Controller 独立验证最终修复，CC 审查，按交付审批整合回 dev。
7. 在安全节点停止相关写入、保存状态并更新 dev 软件。
8. 重启后检查原有任务能否从已有 Session/Run 和检查点正常恢复，核对预算及已完成任务记录。
9. 无法保证安全恢复时，明确说明风险并要求用户确认；不得重复执行已完成的危险操作。

main 不会自动知道 dev 的全部运行状态。自动故障发现、脱敏上报、诊断转交和恢复编排只有实现并验收后才能称为产品能力；目前作为未来目标，必要信息通过已授权的显式方式交接。

## 七、dev 发布 main 的要求

正式发布至少满足以下条件，并记录命令、结果、证据路径、验证版本和来源提交：

- 完整 Controller 回归通过。
- GUI 单元与集成测试通过。
- 实际 Electron 关键交互检查通过。
- 原有主要功能没有明显退化。
- 变更文件、Git Diff 和来源提交可追溯。
- 必要的 UI 修改经过真实界面检查。
- 预算、任务恢复、日志与数据兼容性经过检查。
- 用户明确批准此次正式发布，批准绑定可核对的待发布提交和范围；范围改变时重新确认。

发布前检查 main 与 dev 最新状态和用户修改，保存可恢复的已验证稳定版本及必要状态备份，明确回滚点。按正常 Git 历史合并，不允许强制覆盖 main、丢弃用户修改或默认远程推送。正式发布授权不自动包含远程推送或部署授权。

发布期间应确保软件处于安全更新状态。失败时优先恢复已验证版本；涉及数据格式变化时须核对备份和兼容性，不得只回退代码后宣称数据已恢复。无法可靠回滚时保留现场并报告，由用户决定下一步。

## 八、开发权限与职责

Claude Code 和 Codex 保留各自正常使用时的原生工具能力，不通过禁用 Shell、文件、网络、MCP、Skills 等工具削弱它们。

- Claude Code：主要规划和审查，也允许必要时直接修改代码；继续遵守既有关于小问题修复和重大架构确认的边界。
- Codex：主要实现、调试、测试和修复。
- Controller：调度、预算、审计、独立验收和恢复，保留正式交付审批。
- 用户：决定目标、重大变更及正式发布。

上述职责是协作分工，不是工具权限限制。完整原生工具权限不代表可以未经授权修改无关项目、发布远程版本、扩大预算或覆盖用户数据。项目规则不是操作系统级沙箱；文档中的目录约束和 Git Worktree 也不能提供该级别的强制权限隔离。

## 九、并行开发与冲突处理

不同任务可以并行开发，每个任务使用独立分支和 Worktree；同一 Run 内 Agent 仍顺序调度。不允许两个 Agent 或两个软件实例同时对同一开发分支无协调写入。

修改重叠文件时，必须明确集成顺序、责任方及检查范围。开发完成不等于自动合并。整合前核对最新 dev、基线变化、Git Diff、用户已有修改、来源提交和最终测试结果；合并后验证组合结果，不能只使用各任务合并前的测试替代。

dev 正在运行任务时，不直接替换其正在使用的代码。合并冲突无法可靠解决时停止并报告，保留冲突与现场，不擅自舍弃某一方修改。

## 十、异常、数据与恢复

重要开发活动应记录任务 ID、发起软件版本、Git 基线分支与提交、任务分支、工作目录、Run/Session、授权预算、变更、测试、审查、交付审批和发布决定。只做文档或只读检查且没有 Run 时应如实注明，不制造虚假 Run 记录。

必须遵守以下边界：

- 不把 Mock 通过冒充真实 Agent 验收。
- 不把 AI 自测冒充 Controller 独立验收。
- 不把 Git Worktree 当作操作系统级权限隔离。
- 不把 Git 提交成功当作软件功能验收通过。
- 文件冲突、数据归属不明或恢复状态异常时，保留现场并停止受影响的写入。
- 严禁未经确认删除真实项目或历史运行数据。
- 不将凭据、密钥、认证副本和敏感日志纳入 Git 提交；添加文件前逐项核对，禁止为方便交付而将整个工作区批量纳入提交。
- 暂停或异常时续接已有 Session/Thread，保留真实调用计数和已执行操作，不以重建任务清空预算或恢复证据。

## 十一、规则维护

本文件作为长期治理规则 V1。后续修改必须记录版本、日期、变更原因和影响，并检查 AGENTS.md、CLAUDE.md、统一工作规则、项目执行契约及其他有效约定的冲突。

重大权限、分支发布或用户数据政策变更需要用户批准。任何 Agent 不得为了完成当前任务私自弱化治理要求。规则描述必须区分“现在已经实现”“本规则要求遵守”与“未来计划实现”；实现能力变化后用验证证据更新状态说明。
