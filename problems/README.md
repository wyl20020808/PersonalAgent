# PersonalAgent 持续实战改进与问题反馈规则 V1.2

版本：V1.2。修订日期：2026-10-12。按用户要求，将登记范围明确为开发过程中的自省发现，排除用户已交办问题的重复登记；保留已登记问题的解决历史及 `【已解决】` 前缀，不改变开发、验收和交付授权。

适用范围：所有参与 PersonalAgent 开发、执行、规划和审查的 Agent。

长期原则：**实战驱动开发，自省发现自身问题，留下需要后续处理的记录，按影响程度逐步修复，不追求初期功能全面完善。**

## 1. 实战优先

PersonalAgent 是持续迭代的软件。优先让已有功能投入实际使用，在真实开发任务中暴露问题，再根据实际影响不断完善。

不要求初期一次性解决全部潜在问题，不为了追求理论完整性而无限扩展架构、测试或管理流程。

## 2. 所有功能和规则都接受反馈

本规则是一套 Agent 在开发过程中的自省机制，不是用户需求清单或所有修复任务的归档机制。登记对象是执行任务时主动发现、超出用户已交办问题本身、具有实际影响且需要后续处理的缺陷或改进点。问题类型包括但不限于：

- 功能 Bug、异常、崩溃和错误行为。
- 功能设计不合理、缺失或使用体验差。
- Agent 规划、执行、审查中的错误或误判。
- Agent 对项目结构、模块、代码、接口、依赖理解不足。
- Project Context、长期记忆、模块记忆不准确、过期、遗漏、冗余。
- 文档结构不合理、文档难以定位、知识读取不充分或低效。
- Prompt 冗余、上下文选择不准确、Token 和工具调用浪费。
- Agent 工具权限、模型适配、Session、Run、恢复与交付流程中的问题。
- 任务过程中重复劳动、无效返工、效率低下。
- 影响安全性、可靠性、维护性和后续扩展的潜在问题。
- 任何真实执行过程中发现的其他有价值的改进点。

以上范围不是封闭清单。

## 3. 登记自省发现，避免重复记录用户任务

开发过程中自行发现符合第二节范围、尚需后续处理的问题时，应记录到 PersonalAgent 仓库的 `problems/` 目录，每个问题一个 Markdown 文件。命名建议为 `YYYY-MM-DD-简短问题名.md`。

登记前按以下边界判断：

- 用户明确提出并交办解决的问题：直接修复、验证并报告任务结果，不因本规则自动新建问题记录；未解决或受阻时也先写任务进度与阻碍，不将用户任务复制成自省记录。用户明确要求登记时，按其要求记录。
- 修复用户问题时查明的直接原因、实施步骤、正常调试失败及验证结果：属于该任务的处理记录，不作为额外自省问题登记。
- 执行过程中额外发现的自身缺陷、错误判断、流程漏洞或效率问题，且仍需后续处理：登记实际证据、影响和下一步，不扩大当前任务范围。
- 本轮自行发现并当场解决、没有后续处理事项的问题：写入任务结果或验证记录即可，不强制新建问题文件。
- 已有问题记录被本轮解决：更新原记录并加 `【已解决】` 前缀，不重复新建。

例如：用户要求修复计时、头像及暂停按钮，修复后报告验证结果即可，不自动新建同名问题记录；开发中额外发现 Agent 反复读取无变化的完整日志、影响效率且本轮未处理，才按本规则登记。

本目录保留已登记自省问题的解决历史。保留历史不意味着每个已完成的用户修复任务都要补建问题记录。

记录保持精简，包括：

- 问题现象。
- 发生场景、相关功能或模块。
- 实际影响。
- 可核实的证据或复现线索。
- 已确认原因或待验证的猜测，两者必须区分。
- 当前状态：待处理、处理中、已解决或暂缓。
- 建议的下一步。

只记录有证据的事实，不编造根因。同一个问题重复出现时，优先补充已有记录，不反复创建重复文件。

问题可能属于 PersonalAgent 本身，也可能属于它正在开发的外部项目。必须区分归属：PersonalAgent 自身的功能问题记录在本仓库 `problems/`；外部项目自身的问题原则上记录在该项目获授权的目录。若当前没有跨项目写入权限，应在任务报告中说明待登记事项，不得绕过项目隔离擅自写入其他仓库。

## 4. 不阻断正常开发

- 普通问题：记录后继续当前开发任务，不要求立即修复。
- 明显影响当前任务正确性的问题：根据现有流程返工、暂停或请求人工处理。
- 可能导致数据破坏、跨项目错误写入、未经授权操作、审计失效等严重问题：及时停止受影响操作并保留证据。

不得为了记录问题而启动额外付费 Agent Run。

## 5. 持续解决与反馈

后续开发时，可以参考 `problems/` 中与当前任务有关的记录，优先解决反复出现、实际影响较大的问题。

修复后更新原问题状态，并记录实际验证结果。如果修复没有解决根因，重新标记待处理。禁止只为了关闭问题而虚构完成结果。

已登记的问题确认已解决后，必须在原文件名最前面加上 `【已解决】`，例如 `【已解决】YYYY-MM-DD-简短问题名.md`，并同步更新指向旧路径的链接或索引。已带前缀时不重复添加。保留原文件中的问题、修复和验证证据，不因解决而删除历史记录。已有记录在本轮确认解决或更新为已解决时，同样适用。此前没有登记的用户修复任务，不为了添加前缀而补建问题文件。

仅部分解决或仍有该问题必需的验证未完成时，不得标为整体已解决，也不得添加前缀；应明确剩余问题与验证边界。已解决问题再次出现，或后续证据证明根因未解决时，去掉 `【已解决】` 前缀，更新为待处理或处理中，并记录重新打开的原因。

每次开发任务结束时，Agent 应简短检查是否额外发现符合上述范围、需要后续处理的自身问题；没有则不登记，不为完成自省检查而制造问题或报告。

## 6. 遵守既有治理

本规则不替代：

- [AGENTS.md](../AGENTS.md) 开发治理。
- Project Context V1.1。
- Controller 的正式审查。
- 现有项目写入隔离。
- Delivery 人工审批。
- Git 分支和 Worktree 规则。

问题记录属于改进反馈，不等于自动授权修改源码、切换模型、跨项目写入或执行危险操作。

不新增问题数据库、后台自动巡检、复杂状态机或新 UI。

## 7. 问题登记后的用户告知

任何 Agent 在执行任务过程中，只要新建了 `problems/` 下的问题记录，就必须在本轮面向用户的最终回复中主动告知新建的问题文档路径、问题的简短描述、当前状态，以及是否影响本轮任务。

如果更新了已有问题记录，且新增了重要证据、处理进展或状态变化，也应简要告知，并明确是“更新”而不是“新建”。即使本轮任务失败、暂停或未完成，只要问题文档已经写入，也需要在回复中说明。

如果没有实际创建或更新文件，不得声称已经记录；如有待登记的问题，应如实说明。

告知不要求用户立即处理问题。普通问题记录后继续开发，严重问题仍遵守现有暂停与安全规则。不需要重复展示全部历史问题，也不增加冗长报告。

建议最终回复格式（更新已有记录时，将标题改为“本轮更新问题记录”）：

**本轮新增问题记录**

- 文件：`problems/xxx.md`
- 问题：一句话描述
- 状态：待处理 / 处理中 / 已解决 / 暂缓
- 影响：是否阻碍当前任务
